# 调课与代课算法检查（2026-10-13）

范围：检查当前算法，不修改实际课表或业务代码。采用 SQLite 内存数据库直接调用现有候选、预览、保存和代课函数；规则目录和课位加载用隔离数据替换，规则评估使用真实实现。

## 结果

7 个基础场景符合预期：空位移动、普通同班对调、源教师撞课拦截、对方教师撞课拦截、工作日与周六不能混调、整课不能与半课互换、周六半课可从单周改到双周。

### 1. 候选、预览与保存的硬规则判断不一致（高）

设置教师周四第 2 节禁排，源课为周三第 1 节。

- 候选 options：available=true。
- 预览 preview：available=false，真实规则评估识别 teacher_forbidden_slots 违规。
- 保存 move：force=false 仍成功，课表真实记录落到周四第 2 节。

原因：候选主要检查课位通道和教师撞课；预览额外运行 _rule_checks_after_adjustment；最终 move_schedule 不运行这一规则检查。不能把预览当成保存的保障。

### 2. 共享教室占用未检查（高）

源课使用 shared-room，将其移动到其他班已经使用同一教室的时段，两名教师不同。算法返回 available=true。移动和对调需要分别检查两端的教室占用，不能只看教师和本班。

### 3. 单双周两条相同记录未按整课识别（中，取决于记录形态）

目标课位有单周和双周两条同教师同科目记录，彼此不冲突，相当于每周都有同一课。整课调入时 _class_peers_at 返回两条，算法以 len(peers)>1 判定“课程重叠”而拒绝。若业务允许这种存储形态，应先归并成逻辑课程，连同两条记录进行原子移动；真正重叠的课程仍须拦截。

### 4. 代课后无法继续调课（高）

另一老师具有学科代课资格，但没有该班 TeachingAssignment。代课保存成功后，Schedule.teacher_id 更换，TeachingAssignment 不变。再次查候选时，所有目标均被“教师未配置该班该学科的任教关系”拦截。

需要区分原任课关系与代课事件，调课校验应识别有效的代课安排；不宜通过永久新增任课关系掩盖问题。

### 5. 临时代课实际改写周期课表（高，语义不一致）

界面说明适合病假、事假临时顶课，但 ScheduleSubstituteIn 只有 schedule_id、academic_year、term、teacher_id，没有具体日期或有效区间。保存直接修改周期 Schedule.teacher_id，因此不是只影响某一次上课，也没有独立代课恢复记录。

## 建议修复顺序

1. 统一候选、预览、保存的校验入口；最终保存重新检查全部硬约束，教师禁排与资源冲突不接受普通勾选覆盖。
2. 补齐教室双向冲突判断。
3. 明确半课与整课的逻辑分组，确保单双周课时守恒。
4. 独立建模临时代课的日期或区间，保留任课关系与调整历史；如果提供永久换教师，使用单独操作。
